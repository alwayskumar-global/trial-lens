# Hand-built abstention test set (TASKS Phase 3; AUTHOR-CREATED, FICTIONAL, NOT clinician reviewed)

Status 2026-10-07: 30 cases authored, run offline once, **30 of 30 match their pre-written expectations. The TASKS item stays OPEN until Kumar reviews the cases and results.** This is a development check of the deterministic engine layers. It is **not** product validation, it is not an accuracy figure, and no model, network or visitor input is involved.

**Files.** `eval/abstention/cases.ts` (cases, expected outcomes, rationales; committed in `84cef6b` BEFORE any case was run), `eval/abstention/run-case.ts` (runs one case through the real engine), `eval/abstention/run.ts` (`pnpm exec tsx eval/abstention/run.ts`, expected vs actual table), `eval/abstention/abstention.test.ts` (35 vitest tests), `eval/abstention/inspect-internals.ts` (diagnostic: how each typed case was decided). `toLoaderSet()` exports the cases in the harness loader format (AMBIGUOUS exported as gold UNKNOWN because the loader's gold has no AMBIGUOUS).

**Layers and what an expected outcome means.** Each case has one expected criterion status, one expected tier and, for pregnancy cases, one expected panel result; they belong to different layers and are never alternatives. `typed` = hand-written parser output -> `reconcileBatch` (coverage/scope vetting) -> `assessCriterion` (clause evaluation) -> `applyAbstentionGuard`. `model_finding` = a fixture free-text finding -> `applyAbstentionGuard`. Tier = a one-criterion trial after `tierTrialCeiled` (TIER_UNKNOWN_THRESHOLD 3, R2 ceiling). Panel = `studyTeamQuestions` for a one-study trial. Pregnancy cases follow the current engine and panel (the answer path was removed): `pregnant=false` does not satisfy a negative pregnancy test or its timing; contraception requirements stay unresolved without their own evidence; childbearing potential is never inferred from age, sex or menopause. Conditional cases allow a vacuous PASS only when non-applicability is proven by a known fact (ab-25); unrepresented or unproven conditions stay UNKNOWN (ab-26, ab-27, ab-30).

**Groups (30):** fact known 6 (ab-01..06), fact absent 6 (07..12), uncertain 4 (13..16), clinical judgment 4 (17..20), unsupported evidence 4 (21..24), conditional 3 (25..27), pregnancy 3 (28..30). Expected statuses: PASS 5, FAIL 2, UNKNOWN 22, AMBIGUOUS 1.

**Result (run once, after the cases were committed):** 30 of 30 match. Mechanisms confirmed from the internals diagnostic: ab-17, 18, 19, 28 and 30 were decided by vetting (`atoms_downgraded`), ab-25 PASS cites `age` with applicability `not_applicable`, ab-26 and ab-27 show applicability `unknown`.

**Limits, stated plainly.**
1. The author knew the engine's rules when writing expectations, so agreement shows the code follows its documented rules on these inputs; it does not show the rules are clinically right.
2. Parser output is hand-written, so this does not test the parsing model.
3. ab-28 and ab-30 were stopped at vetting (a negated `false` assertion; unaccounted words), not by the dedicated semantic guards (`pregnancy_test_is_not_pregnancy_status`, source-must-mention-fact). Those guards are not isolated by this set; a case that passes vetting but trips only the semantic guard is a candidate addition, not written.
4. The abstention guard checks that cited keys are known, not that they are relevant: a PASS citing an irrelevant known key would survive. Not tested here (no expected outcome was written for it); it is a known property of the guard.
5. One criterion per trial: multi-criterion tier interactions and the unknown-count threshold are not exercised.
6. Not clinician reviewed; fictional wording and values; no real patient or dataset text.

No model call, visitor input, replay backfill or Production change.

## Additions: guard isolation and relevance negative control (2026-10-07; reported separately; the original 30 cases are unchanged)
Files: `eval/abstention/isolation.ts` (expected values committed in the commit before any run), `run-isolation.ts` (`pnpm exec tsx eval/abstention/run-isolation.ts`, exits 1 on a mismatch), `isolation.test.ts`. 7 additional cases: **5 match, 2 mismatch.**

**Guard isolation, 4 of 4 match.** Each input is built to survive vetting and reach the guard; the test asserts, separately, vetting status `ok` (an earlier rejection is not counted as a guard pass), that the leaf is still an atom, that `atomProblems` is EXACTLY the guard's reason, then partial completeness and a final UNKNOWN with no evidence. `pregnancy_test_is_not_pregnancy_status`: iso-01 (exclusion "Pregnancy-test", pregnant=true known) and iso-02 (inclusion "hCG-pregnancy"). `source_does_not_mention_fact`: iso-03 ("Treated stable" for cns_mets=treated_stable) and iso-04 ("III" for stage III). Reasoned (not executed) counterfactual: without the guard each known fact would decide the atom (FAIL, PASS, PASS, PASS). **Reachability finding:** natural wording cannot reach these guards because vetting already rejects any source word the fact's cue, value or unit does not account for ("test", "serum", "urine", "hCG"); only constructed sources (a hyphenated "Pregnancy-test", or a source made only of value words) pass vetting. The guards are therefore a second line of defense whose isolation inputs are artificial; this says nothing about how often a parser would produce such sources.

**Relevance negative control, 2 expected-UNKNOWN cases FAIL (kept visible).** rel-01: a PASS citing the known but irrelevant `age` for "Hemoglobin of at least 9 g/dL" (hemoglobin absent) survives as **PASS** (expected UNKNOWN). rel-02: a FAIL citing known `sex` and `ecog` on "Active cardiac disease" survives as **FAIL**, tier UNCERTAIN (expected UNKNOWN, POSSIBLE). The positive control rel-03 (a PASS citing the criterion's own known hemoglobin) correctly survives. The expectations were not changed. In the test file the two failing controls use `it.fails` ("KNOWN FAILURE ...") so the suite stays runnable while the gap is explicit; they start failing as tests the moment a relevance check is added, which is the cue to remove `it.fails`. `run-isolation.ts` prints them as MISMATCH.

**Proposed conservative relevance check (NOT implemented; awaiting review).**
- *Rule:* in the free-text evaluation path, every key cited by a PASS or FAIL must belong to that criterion's own parsed dependencies, the keys of its atoms plus the `depends_on` of its text leaves (`dependsOn(clause)` in `src/lib/engine/clause.ts`); otherwise the finding becomes UNKNOWN with `guard_downgraded`, like the existing guard. A criterion whose clause declares no dependency cannot receive a free-text PASS/FAIL (conservative).
- *Wiring:* `applyAbstentionGuard(finding, profile, allowedKeys?)` gets an optional third argument; the `evaluate` stage in `src/lib/pipeline/run.ts` passes `dependsOn(outcome.clause)` per item. The typed (code) path is unaffected (its evidence is already the compared atoms).
- *Why structural, not keywords:* it uses the parse's declared dependencies, not word matching on the criterion text, so it avoids loose cue lists.
- *Limits:* the declared `depends_on` is parser-produced and not itself verified here, so a parser that wrongly declares `age` for a hemoglobin criterion would defeat it; it only narrows (never lets more through); it may lower recall where a parser omitted a needed dependency, which is unmeasured (a possible offline measurement over saved parses, no model call, needs approval).
- *Acceptance if approved:* rel-01 and rel-02 become UNKNOWN with the `it.fails` removed, rel-03 and all 30 original cases and the existing 706 tests unchanged, plus new tests for the empty-dependency and wrong-key paths.

## Relevance check: how a dependency is VERIFIED, and the offline impact (2026-10-07; for review; NOTHING WIRED)
**The two relevance failures (rel-01, rel-02) remain open and visible (`it.fails`).** A green suite does not close them: the suite is green only because those two tests are marked as expected failures. No guard change has been made; `applyAbstentionGuard` and the pipeline are untouched.

**Why "declared by the parser" is not enough.** `depends_on` on a text leaf is produced by the parser and is checked against nothing. A parser that declares `age` for a hemoglobin criterion would let a PASS citing `age` through a declared-dependency rule.

**Proposed verification (`src/lib/engine/dependency-verify.ts`, pure, unwired, 7 tests in `dependency-verify.test.ts`).** A key is VERIFIED for a criterion only if the leaf that declares it (a) declares it (`depends_on` or atom `fact_key`), (b) carries a cue for that key in the leaf's OWN `source` (an exact fragment of the original criterion text, already enforced by the batch schema and the vetting), and (c) for an atom leaf, has no semantic problem (pregnancy-test, receptor-threshold, ...). The check is local to the declaring leaf, so another leaf's wording cannot vouch for it. A finding would then pass only if every cited key is verified (an empty citation list is not relevant). Tests: a parser that falsely declares `age` for "Hemoglobin of at least 9 g/dL" gives declared [age], verified [], and a PASS citing `age` is rejected (the rel-01 shape); the correct declaration verifies `hemoglobin` and a PASS citing it is accepted (the rel-03 shape); one irrelevant key among the cited keys is enough to reject; an undeclared but relevant key is not added; another leaf's wording cannot vouch (leaf-local); an unsound atom does not verify its key. **Documented limitation (also a test):** the shared cue table is LOOSE, so "Hemoglobin of at least 9 g/dL in adults" with a false `age` declaration IS verified by the word "adults". The cue is injectable; a production version needs a strict, anchored per-key table (as `study-questions.ts` already has for two noisy keys), and a test shows a strict age cue rejecting that case. The strict table does not exist yet.

**Offline impact (read-only; `eval/relevance-impact.ts`, selects only (a test enforces it), no model call, no write; counts only, `eval/reports/relevance-impact-offline.json`; the three prepared FICTIONAL profiles' stored results and the cached public-criteria parses).** Variant A = cited keys must be among the parser-DECLARED dependencies; variant B = declared AND verified by the loose cue (B accepts at least what a strict table would, so its downgrades are a LOWER BOUND of a strict table's). A and B gave identical counts.

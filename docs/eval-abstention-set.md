## Relevance check: how a dependency is VERIFIED, and the offline impact (2026-10-07; for review; NOTHING WIRED)
**The two relevance failures (rel-01, rel-02) remain open and visible (`it.fails`).** A green suite does not close them: the suite is green only because those two tests are marked as expected failures. No guard change has been made; `applyAbstentionGuard` and the pipeline are untouched.

**Why "declared by the parser" is not enough.** `depends_on` on a text leaf is produced by the parser and is checked against nothing. A parser that declares `age` for a hemoglobin criterion would let a PASS citing `age` through a declared-dependency rule.

**Proposed verification (`src/lib/engine/dependency-verify.ts`, pure, unwired, 7 tests in `dependency-verify.test.ts`).** A key is VERIFIED for a criterion only if the leaf that declares it (a) declares it (`depends_on` or atom `fact_key`), (b) carries a cue for that key in the leaf's OWN `source` (an exact fragment of the original criterion text, already enforced by the batch schema and the vetting), and (c) for an atom leaf, has no semantic problem (pregnancy-test, receptor-threshold, ...). The check is local to the declaring leaf, so another leaf's wording cannot vouch for it. A finding would then pass only if every cited key is verified (an empty citation list is not relevant). Tests: a parser that falsely declares `age` for "Hemoglobin of at least 9 g/dL" gives declared [age], verified [], and a PASS citing `age` is rejected (the rel-01 shape); the correct declaration verifies `hemoglobin` and a PASS citing it is accepted (the rel-03 shape); one irrelevant key among the cited keys is enough to reject; an undeclared but relevant key is not added; another leaf's wording cannot vouch (leaf-local); an unsound atom does not verify its key. **Documented limitation (also a test):** the shared cue table is LOOSE, so "Hemoglobin of at least 9 g/dL in adults" with a false `age` declaration IS verified by the word "adults". The cue is injectable; a production version needs a strict, anchored per-key table (as `study-questions.ts` already has for two noisy keys), and a test shows a strict age cue rejecting that case. The strict table does not exist yet.

## Fail-closed design and offline projection (2026-10-07; for review; NOTHING WIRED; supersedes the declared-dependency / loose-cue options above)
**rel-01 and rel-02 remain open and visible (`it.fails`).** The two earlier options (declared dependencies, declared plus loose cue) are withdrawn as the basis of any check: neither gives independent proof (the parser declares, the cue is loose). Nothing below changes the pipeline or `applyAbstentionGuard`.

**Rule (proposed).** A free-text PASS or FAIL becomes UNKNOWN (evidence cleared, guard-downgraded) unless the ENTIRE finding has independently provable support, meaning the code evaluation of the whole vetted clause reaches the SAME status and every cited key is among the facts that evaluation actually compared (`acceptFreeTextFinding`, `src/lib/engine/fail-closed.ts`, pure, unwired). UNKNOWN and AMBIGUOUS pass through. The model's claim, a declared `depends_on` and a cue in the wording are never proof.

**How a compound criterion's full requirements are established.** A criterion is the AND of its blocks; each block is IF(when) THEN items (all/any) EXCEPT exceptions. Code evaluates this tree three-valued; only executable atoms (known fact, comparable value and unit) can be established. A text leaf, a timing leaf, a rejected atom or a wholly rejected criterion is NOT established. Hence: PASS needs every required requirement established (all conjuncts true; for an exclusion, every disjunct false; a conditional block needs its non-applicability proven by a known-false atom); FAIL needs one required requirement established false (sound, a single failed conjunct is enough); anything else is UNKNOWN. A key that appears in the wording, or that the model cites, proves nothing about the other requirements. Tests (`fail-closed.test.ts`, 10): hemoglobin at least 9 g/dL AND no history of cardiac disease, two blocks, a PASS citing both known keys is rejected because the negated cardiac requirement is a text leaf; a FAIL with hemoglobin 8 is accepted only because code derives the same FAIL; an exclusion "CNS metastases or cardiac disease" with only cns_mets known: a PASS citing cns_mets (a relevant key) is rejected, and it is accepted only when both disjuncts are proven false; a FAIL citing an extra key the evaluation never compared is rejected; the rel-01 shape (age for hemoglobin) is rejected. Finding recorded while building them: when a negated text leaf shares a block with an atom, the vetting already downgrades the atom (`negation_elsewhere_in_block`), a further fail-closed protection; my first draft of that fixture was wrong about it and was corrected, not the engine.

**Atoms downgraded to text.** The vetting's `toText` keeps the atom's `fact_key` inside the text leaf's `depends_on`, and an atom that survives vetting but fails a semantic guard still appears in `dependsOn(clause)`. Design: every leaf gets a provenance (`leafProvenance`): `executable_atom` (the only authoritative origin), `atom_rejected_vetting`, `atom_rejected_semantic`, `parser_text`, `parser_timing`, `criterion_rejected`. Keys of non-authoritative leaves are retained for display only and are excluded from `authoritativeKeys`; a rejected atom's retained key never supports a finding (tests: HER2-low IHC wording, and "Pregnancy-test"). The cached parse does not record which leaf was rejected, so persisting provenance needs a cached-parse schema addition and a parser-version bump (not done); the projection below uses the criterion-level vet status as a proxy.
